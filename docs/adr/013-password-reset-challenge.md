# ADR-013: 비밀번호 재설정의 시도 제한과 인증코드 일회성 소비

- 날짜: 2026-09-12
- 상태: 채택, 로컬 구현·실제 Redis/MySQL 및 전체·프론트 회귀 검증 완료
- 관련: [작업 기록](../portfolio/work-logs/2026-09-12-password-reset-protection.md)

## 문제

기존 재설정은 Redis에서 코드를 읽고, MySQL에 비밀번호를 저장한 다음 Redis 코드를
삭제한다. 읽기와 삭제가 분리되어 같은 코드를 읽은 두 요청이 모두 비밀번호를 바꿀 수
있다. 발송 간격·횟수와 오입력 횟수에도 서버 제한이 없다. 기존 이메일 키는 이메일을
재사용한 새 계정을 구분하지 못한다.

## 결정

전용 `PasswordResetChallengeStore` port와 Redis Lua adapter를 둔다. 기존 범용
`RedisComponent`의 다른 사용처는 유지한다. Redis에서 상태 확인과 변경을 한 스크립트로
실행하여 발송 예약, 오입력 차감, 정답 소비를 각각 원자적으로 처리한다.

회원은 먼저 현재 DB에서 찾고, Redis 제한과 challenge는 불변 회원 PK에 결합한다.
이메일 문자열만 서로 다르게 적어 같은 계정의 제한을 우회하지 않도록 한다. 현재 활성
회원과 활성 회사에 한해 발송·재설정한다. 코드 소비와 BCrypt 처리 후 별도 transaction의
updater가 같은 PK/email/company와 활성 상태를 다시 조회하고 잠근 뒤 비밀번호를 저장한다.
Redis·SMTP 지연 동안 DB row lock을 잡고 기다리지 않는다.

- 발송: 계정당 최소 60초 간격, 첫 예약부터 고정 1시간 창 안에 최대 5회.
- 코드: 기본 유효시간 10분, 오입력 최대 5회. 서버 Redis TTL이 권위 있는 만료 기준이다.
- 소비: 정답일 때만 원자적으로 소비하고, 동시에 제출한 동일 코드는 최대 한 요청만
  MySQL 변경 단계로 진행한다.
- 실패: 코드 소비 후 DB rollback 또는 commit 결과 불확실성이 생겨도 코드를 복원하지
  않는다. 사용자는 발송 제한 안에서 새 코드를 요청한다.
- SMTP 실패: 해당 발급 ID가 아직 현재 challenge인 경우만 무효화한다. 늦게 끝난 이전
  발송의 실패가 이후 발송 코드를 삭제하지 않는다. 발송 실패도 예산에서 차감한다.

SMTP 오류 뒤 Redis 취소까지 실패하면 원래 발송 오류를 반환하며 challenge는 TTL까지
남을 수 있다. 발송과 정리가 모두 불확실한 상황을 성공으로 응답하거나 예산을 환불하지
않는다. SMTP 오류가 수신함 미도착을 증명하지 않으므로 프론트는 새 코드 요청을 안내한다.

Redis와 MySQL을 하나의 transaction으로 묶지 않는다. 코드를 복원하는 보상은 MySQL
commit 여부가 불확실할 때 이미 성공한 코드를 되살릴 수 있다. 이번에는 재시도 편의보다
한 번 사용한 코드의 재사용 거부를 우선한다. 이것은 비밀번호 변경 성공을 반드시 한 번
보장한다는 뜻이 아니다. 소비 직후 프로세스가 종료되면 변경 없이 코드만 소진될 수 있다.
Lua의 실행 원자성도 스크립트 오류 시 이전 쓰기를 rollback한다는 뜻은 아니다. 오류가
발생한 발송 시도에서도 예산이 보수적으로 차감될 수 있다. 또한 고정 시간 창이므로
임의의 연속 60분마다 반드시 발송 5회 이하라는 rolling window 보장은 아니다.

기존 POST `/api/auth/verify-code`, PUT `/api/auth/password` 요청 형태와 성공 200은 유지한다.
잘못된 코드 400(`13000`), 한도 초과 429(`13006`), 서버 장애 500을 구분하고 프론트에
재시도 방법을 표시한다. 오입력 1~4회는 400, 5회째와 이후 요청은 정답이어도 429다.
429에 정확한 잔여 시간 응답을 추가하지 않으므로 UI의 60초 표시는 시간 창 한도 해제를
보장하지 않는다.
프론트의 타이머·중복 클릭 차단은 사용성 보조이며 서버 제한의 대체 수단이 아니다.

SMTP는 DB transaction 밖에서 호출한다. 직접 만드는 `JavaMailSender`에 연결/읽기/쓰기
timeout을 각각 기본 5,000ms로 설정하고 양수만 허용한다. 여러 I/O가 발생할 수 있으므로
전체 발송 요청이 5초 이내 끝난다는 보장은 아니다.

## 대안

| 대안 | 장점 | 비용·문제 |
| --- | --- | --- |
| 기존 GET 후 DELETE | 단순함 | 동시 소비와 오입력 제한을 보장하지 못함 |
| Redis 원자 소비 후 DB 변경 | 코드 단위 최대 한 번 진입, 기존 Redis 활용 | DB 실패에도 새 코드 필요 |
| MySQL challenge 테이블과 비밀번호 동시 commit | 한 DB transaction으로 원자성 구성 가능 | schema·만료 청소·발송 상태·배포 범위 확대 |
| 분산 lock·소비 후 복원 | 실패 후 같은 코드 재시도 가능성 | lock 만료·프로세스 종료·commit 불확실성·보상 경쟁 설계 필요 |

## 전환과 한계

이전 Redis 코드와 새 구조 사이에 추측하는 호환 경로를 두지 않는다. 변경 배포 후 기존
코드 사용자는 새 코드를 발급받아야 한다. 새 key는 `thisway:password-reset:{memberId}:*`이며
기존 `custom.verification-code-expiration-millis`와 `custom.verification-code-key-prefix` 설정은
제거했다. 유효시간은 Lua의 600,000ms 정책으로 고정한다. 같은 회원의 세 key는 같은 hash
slot을 사용하지만 이번 검증은 단일 Redis이며 Cluster 장애·failover 검증이 아니다.
운영 Redis를 지우거나 운영 배포를 수행하지 않는다.

현재 사용자 없음 응답을 통합해 계정 존재를 숨기는 기능, IP/전체 서비스 발송 예산,
CAPTCHA, Redis failover/persistence 보장, SMTP 실제 수신, 비밀번호 변경 시 기존 JWT
영구 폐기는 별도 작업이다. TTL과 한도는 동작 정책이며 운영 부하 측정으로 도출한 수치가
아니다. 작은 테스트 결과를 대규모 공격 방어·서비스 전체 발송 상한으로 일반화하지 않는다.
Redis에는 코드와 이메일의 SHA-256을 저장한다. 원문 저장을 줄이는 조치이며 6자리 코드의
작은 후보 공간 때문에 Redis 내용 탈취 후 offline 추측을 막는 보장으로 표현하지 않는다.

실제 Redis·MySQL 회귀와 프론트 검증 결과, 정확한 오류 계약과 제한은 작업 기록에 확정한다.
