# ADR-009: 차량 현재 상태를 Power 이벤트 시각으로 정렬

- 날짜: 2026-09-06
- 결정: 채택, 차량 현재 상태 projection에 한정
- 관련: CHANGE-027, CHANGE-031, P1-02

## 문제

차량 행 잠금은 요청 처리를 직렬화하지만 발생 순서를 복원하지 않는다.
12시 ON 이후 11시 OFF가 도착하면 기존 코드는 현재 차량을 OFF로 바꿨다.
처리 시각(created/updated time)은 장치 이벤트 발생 시각을 대신할 수 없다.

## 규칙

Vehicle에 nullable `lastPowerEventTime`을 영속화한다. 성공적으로 commit된
Power 이벤트의 현재 상태·좌표만 다음 규칙으로 갱신한다.

| 수신 이벤트 | 차량 상태·좌표·watermark |
| --- | --- |
| watermark 없음 | 첫 수신 이벤트로 초기화, 기존 상태의 실제 시각을 복원했다는 뜻은 아님 |
| 더 최신 시각 | ON/OFF 상태와 해당 이벤트 좌표를 함께 갱신 |
| 더 과거 시각 | 유지 |
| 같은 시각, 같은 상태 | 유지, 충돌 좌표도 최초 반영 값 유지 |
| 같은 시각, 기존 ON/수신 OFF | OFF와 OFF 좌표로 변경 |
| 같은 시각, 기존 OFF/수신 ON | 유지 |

초 단위 프로토콜에 sequence가 없으므로 동시각에서는 OFF를 우선한다. 이는
현대화에서 선택한 보수적 tie-break이며 원 RFP 규칙이나 실제 장치 순서의 증거가 아니다.
같은 초에 실제 재시동한 경우를 정확히 구분하려면 장치 sequence/세션 식별자가 필요하다.
같은 시각·종류인데 다른 좌표를 보낸 충돌은 첫 값 유지이며, 전체 payload의
도착 순서 무관 수렴이나 충돌 검출까지 보장하지 않는다.

## 실행 경계

MDN으로 VehicleReference 조회 → active Vehicle 행 잠금 → 원본 Power 저장 →
OFF 누적거리 max 갱신 → 이벤트 시각에 따른 상태·좌표 갱신 → Trip 처리 → commit.
주소 조회는 기존처럼 AFTER_COMMIT이다. READ_COMMITTED와 같은 차량 잠금을 유지한다.
상태와 watermark는 같은 transaction으로 저장/rollback된다.

이전에는 OFF만 Vehicle 좌표를 갱신했다. 이제 최신 ON도 함께 갱신하여 ON 먼저/과거 OFF
나중 도착과 그 반대 순서에서 서로 다른 과거 좌표가 남는 일을 막는다.
GPS 상태별 좌표 품질 정책은 아직 별도이며 최신 GPS 위치라는 보장은 없다.
누적거리 max는 시간 guard와 독립적으로 유지하고, 과거 원본 Power 및 Trip 처리는 생략하지 않는다.

## 대안

- 도착순 덮어쓰기: 간단하지만 지연 OFF에 현재 상태가 퇴행한다.
- 원본 로그 MAX 조회: 매번 조회 비용이 생기고 동시각 충돌·기존 원본 신뢰성 문제가 남는다.
- 모든 이벤트 재생/Trip 상태 머신 동시 교체: 완전한 모델로 갈 수 있으나 기존 중복 Trip과
  혼합 거리 필드의 마이그레이션까지 필요하다. 이번 작은 변경과 분리한다.

## 호환성과 제한

V6는 컬럼만 추가하고 기존 상태·좌표·거리를 변경하지 않는다. API DTO에는 watermark를
추가하지 않아 응답 필드가 유지된다. 첫 신규 이벤트 이전의 정렬 기준은 알 수 없다.
잘못된 미래 시각은 watermark를 오염시킬 수 있다. 장치 인증·clock skew·strict Power
입력 검증은 후속 gate이며 이 변경만으로 공개 수집 API를 안전하다고 주장할 수 없다.
기존 Trip 중복으로 Trip 처리 자체가 실패하면 Power/Vehicle도 rollback된다.
따라서 이것은 Trip 멱등 상태 머신이나 전체 요청 exactly-once의 완성이 아니다.
